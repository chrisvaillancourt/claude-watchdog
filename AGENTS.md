# watchdog

A Claude Code mod (function-hook plugin): a quiet background reviewer that reads each main-conversation turn and raises severity-tagged notes. `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/policy.ts`: pure decisions and text. Config parsing, command parsing, evidence capture and the compact delta, the reviewer's prompt, parsing its reply, the quarantine, the emission guard, the delivery and wake decisions, status text. No `$`, no I/O. Unit-tested in `policy.test.ts`.
- `hooks/register.ts`: wiring. `session.append` (evidence capture), `turn.start`/`turn.complete` (turn ids, cadence), the review run (`$.model.complete`), delivery (`$.session.append`, `$.prompt.submit`), the `/watchdog` command, the usage log. Tested through the engine in `register.test.ts` and, for the windows between a review's awaits, `races.test.ts`.
- `types/index.d.ts`: the mod's types and its `$.state` contract (`PluginState['watchdog']`). Every `$.state` key the module uses must be declared here.
- `.claude-plugin/plugin.json`: manifest and `userConfig` options. `marketplace.json` makes the repo its own marketplace.
- `scripts/check.sh`: the commit gate (validate, test, typecheck).
- `.claude-plugin/types/` and `tsconfig.json` are generated by Claude Code when it loads the mod from a watched folder. They're gitignored; don't commit or hand-edit them.

## How watchdog works (design invariants)

A passive reviewer for the main conversation. The main model never calls it and never sees its reasoning, only its admitted notes.

1. **Capture.** A `session.append` hook records evidence from main-conversation rows as they are stored: the prompt (door `prompt`), each `tool_use` block of the model's response (door `response`, name and selected arguments) and each `tool_result` (door `tool-result`, an excerpt, errors kept longer). The final answer comes from `turn.complete`'s `answer`. The model's intermediate prose and thinking are never captured: the reviewer gets the ask and the work, not the author's story. Each item is truncated at capture, and the list is capped, so `$.state` stays bounded. `buildDelta` holds the reviewer's evidence to `maxDeltaChars` in total, markers included: it reserves the newest prompt and answer together (cut to share the room), then fills with older items newest first, renders in order, and never drops the reserved pair to fit. Subagent rows (`agentId`), the plugin's own rows (door `note`) and notices are ignored. The hook always relays `next(e)` unchanged; capture is best effort and never blocks a row.
2. **Cadence.** Only main-loop `turn.complete` with `reason: 'answer'` counts. Every `reviewInterval`th such turn schedules a review from a `$.clock.after(0)` timer, so `turn.complete` is never held. Skipped turns' evidence stays queued and goes into the next review. A turn whose prompt came from watchdog itself (its continuation) is never reviewed and doesn't advance the cadence; its evidence rides along with the next review. Interrupted (`aborted`) and failed turns are never reviewed; evidence notes the interruption.
3. **Single flight.** One review at a time, tracked by `running.runId` in `$.state`. A trigger while one runs sets `rerun`, and one more review runs after it. After every `await` the run re-checks that it is still the current run and the same `generation` (bumped by `/clear` and `/watchdog off`); a stale run applies nothing. `session.start` (which also runs after a hot reload) clears a `running` record left by a dropped environment.
4. **Review call.** `$.model.complete` on the `model` option with a fixed system prompt (stable across calls), WATCHDOG.md guidance and the compact delta in the user message, `maxTokens` 1024 and a timeout. Usage is added to the session's totals and appended to `~/.claude/watchdog/<session id>.jsonl` with the outcome, counts and admitted notes, never the raw reply.
5. **Admission.** First the raw reply, before any parsing or truncation (fences and text outside the block included), is quarantined whole (nothing delivered) if it carries an instruction override, or any destructive shell directive (every match of every pattern) that the reviewed evidence doesn't hold word for word, spelled the same way. `extent` reads a directive quote-aware: quoted operands belong to it, and it ends only at a newline, a backtick, or `;`, `|`, `&` outside quotes. Inside double quotes `\"` and `\\` are escapes (other backslashes there are literal). Its words keep their quotes and escapes exactly as written, and nothing is normalized (no NFKC: a directive that only shows once compatibility characters are folded quarantines), because quoting changes what the shell does (`'$T'` vs `"$T"`). Don't evaluate shell semantics to widen the exemption. A directive that can't be vouched for always quarantines, evidenced or not: an ambiguous end (unbalanced quote, line continuation, `<(…)`, heredoc, a backtick inside quotes) or any expansion or glob character (`$`, `*`, `?`, `[`, `~`, `{`). A destructive command inside a wrapper (`sh -c 'rm -rf build'`) always quarantines too: scanning starts inside the wrapper's quote, so its end reads as unbalanced. Evidence directives are found the same way, so tool lines render as `- Tool: input` with the input ending its line. Then it is parsed from its last `<notes>` block (`[concern] x`, `(concern) x`, `concern: x`, `**Concern**: x`; indented lines continue a note). No block, text in the block that reads as no note, an empty reply, an API error or a timeout is "review incomplete", never "approved". Then the emission guard: content-free notes dropped, copies within one review coalesced to the most severe (one delivered, one history entry at that severity), repeats of an earlier note at the same or lower severity dropped (escalation allowed), non-blockers capped at `maxNotes` per review (highest severity first; blockers exempt).
6. **Delivery, guarded by turn id.** Notes are for the turn `forTurnId` the review was started for. The run, generation, on/off state and that turn are re-read after the admission write and immediately before the model row, and the run is re-checked again before the person's notice and toast; a stale run delivers nothing (`hooks/races.test.ts` holds that write open to prove it). A window remains between the last check and the append (the engine has no conditional append), so a row can still land just after a newer turn starts; the row names the newest request the review covered ("Watchdog reviewed work through your request: …", the first 80 characters; with `reviewInterval` above 1 a batch spans several requests) so the model can tell it concerns earlier work. Don't add more rereads: they narrow the window but can't close it. If any newer main turn has started since, nothing reaches the model: the notes are shown to the person as a late notice. Otherwise concerns and blockers are appended as one user meta row (the model reads it on its next request), and nits go to a notice row and a toast (the person sees them; the model doesn't).
7. **Wake.** Only when the reviewed turn is still the last one, it completed normally (not interrupted), no turn is running, the session is interactive, the top note is at or above `continueSeverity`, and the cooldown allows it: after a wake, concerns don't wake again for `immuneTurns` main turns (blockers are exempt). The wake is one `$.prompt.submit` (framed as the plugin's message, never `asUser`). The cooldown arms only after the submit resolved.
8. **Off switch.** `enabled` defaults to `false`. `/watchdog off` stops capture and reviews at once and bumps `generation`, so an in-flight review applies nothing. `/clear` (`session.end` with `reason: 'clear'`) resets evidence, turn ids, history and totals, keeping only the on/off override.
9. **Headless.** Skipped unless `reviewHeadless` is on. Then the review runs inline in `turn.complete` (awaited, since the process exits after the answer), notes are logged with their text, and there is never a wake. Checked on 2.1.310: the meta row appended there resolves but isn't kept in a `-p` transcript, so the log is the record.

Checked live on Claude Code 2.1.310 (Haiku as both agent and reviewer): headless with `reviewHeadless`, a dictated `is_even` bug drew a blocker and a Read call reached the evidence (prompt, tool, answer); interactive in a pty, a concern was appended as a meta row, the wake turn started under the plugin's frame and wasn't itself reviewed, and `/watchdog status` showed the review's tokens. A plugin seated above can bypass the `session.append` hook for some rows (seen at session start). Re-checked headless at the round-2 head with an observer mod on `session.append`: the delivered concern's row was a `user` meta row from origin `plugin`/`watchdog` opening "Watchdog notes on your answer to: …" (since reworded to "Watchdog reviewed work through your request: …").

Never: review a subagent's turns, register or intercept `/advisor`, give the reviewer tools, change the main session's model, system prompt or tool list, or let a raw reviewer reply reach the main conversation unparsed.

## Commands

```sh
scripts/check.sh            # claude plugin validate . && claude plugin test . && typecheck
scripts/check.sh --no-tsc   # when TypeScript isn't available
```

All gates must pass before every commit. A behavior change needs a test in `hooks/*.test.ts` (the `claude-code/testing` kit: `mock.clock`, `mock.store`, `mock.env`, and `on(...)` hooks that stand for the engine beneath the plugin) written first and seen failing for the intended reason, then the change that makes it pass.

To try the mod in a live session: `claude --plugin-dir .` (interactive sessions hot-reload on save), or `claude -p --plugin-dir . "<prompt>"` for a headless run (always loads fresh; hooks that need a terminal won't fire). `claude --debug` logs every skipped hook and refused result.

## Design invariants (apply to every mod built from this template)

- **Main conversation vs subagents.** Events from a subagent's loop carry `e.agentId` (`agent_id` on `classic.*` events). Decide explicitly whether the mod acts on subagents; by default return `next(e)` early for them.
- **Hot reloads reset module variables** (timers included). `register` and `session.start` run again; `$.state` and `$.store` survive. Anything that must persist goes in state or store. Change an atom's `shape` tag when its stored type changes.
- **Never throw out of a hook or timer for reporting.** Logging, status and toasts are best effort. A hook that guards (denies a tool call, drops a prompt) gets a `.catch` that decides fail-open or fail-closed deliberately (`next.called ? next(e) : { deny }`).
- **Headless sessions** (`e.isInteractive === false`, `claude -p`) have no terminal: no panes, `$.ui.notify` fails, `$.session.compact` rejects. Skip or degrade explicitly.
- **Cost and the prompt cache.** Anything that calls a model (`$.model.complete`, `classify`, `fork`, `$.agent.spawn`) is billed to the person. Say what it costs in the README, bound it with options, and don't change the system prompt or tool list per turn (that rewrites the whole prompt cache).

### Engine constraints found the hard way (Claude Code 2.1.29x–2.1.310)

- `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
- `$.session.compact` rejects while a turn runs and in headless sessions.
- A plugin's submitted prompt never expands `@` mentions; `$.prompt.fill` lets the person send it instead.
- `$.model.fork` replays the main thread's last request, which ends before the turn's final answer: quote the answer into the fork prompt if the fork needs it.
- The engine already prefixes `$.ui.status`, `$.ui.toast` and command output with the plugin name; don't add `watchdog:` there. `$.ui.log` lines keep the prefix.
- A model `Write` outside the project raises a permission prompt; have the plugin write its own files with `$.fs.write` (it creates directories). `$.fs.write` replaces the whole file; there is no append.
- `turn.step` hooks are async generators in the path of every request: always pass the stream through (`yield* next({ ...e, effort })`). A rewritten `model` must be a full id (`claude-haiku-5-5`); an alias failed with `unrecognized_model`. Changing `effort` per request keeps the prompt cache (Opus, Sonnet, Haiku 5.5); changing `model` rereads everything uncached. The UI keeps showing the session's model and effort, so surface a rewrite with `$.ui.status`.
- `tool.call`: `const r = await next(e); return { ...r, context: [text] }` adds text the model reads after the tool result and the person never sees; `{ deny: reason }` blocks the call. A `tool.call` hook without `.catch` is reported by validate as a gate: give it one that fails open or closed on purpose.
- Haiku 5.5 rejects `temperature`/`top_p`/`top_k`, `budget_tokens` and assistant prefill with a 400. Prices step up 5x above 100K prompt tokens.
- Side calls (forks, completions, subagents, compaction) use the "everything else" prompt-cache bucket (5m on a subscription), not the main conversation's 1h one. Cache reads still count against plan usage.
- Text a hook injects for the model must not talk about the model's thinking or reasoning ("you can't see it", "doesn't count"): Opus 5.5's reasoning-extraction safeguard refused such a request. Phrase it in terms of the reply and the work.
- Don't build on instructions the model can ignore: a gate that "asks" the model to do something first failed live. Enforce in a hook, or give the model the information and let it decide.
- `/clear` is `session.end` with `reason: 'clear'` and no `session.start` after it: reset per-conversation state there.

### Bugs that recur in these mods (check every change against them)

Reviews of relay, defer-queue and prewalk kept finding the same family: a boolean flag left stale by a late event (track the running `turnId` instead), a message lost on a path nobody tested (a refused submit, a release racing a new hold), a timer or async step acting for a run that was cancelled or replaced (guard with a `runId` and re-check after every `await`), state that survived `/clear` or a reload when it shouldn't (or didn't when it should), and engine state copied into the mod's own flags (decide from facts at decision time). Two review rounds of blockers in the same mechanism means change the mechanism.

### Test kit notes

- A hook that answers an op on `$` (`command.register`, `fs.read`, `model.complete`, `ui.toast`, `session.messages`) returns `{ value }` or `{ deny }`; a hook that answers an event (`session.start`, `turn.start`, `turn.complete`) returns the event's result directly.
- One bottom hook per event per test file (a second registration errors). Test files with JSX are `.test.tsx`.
- Use `mock.clock(on)` and `clock.advance`/`settle` for time; there is no `setTimeout`.
- A throwing mock hook is skipped rather than surfacing its error, so test decisions that depend on an error's text as pure functions in `policy.ts`.
- Any helper that receives `$` must be a top-level function: the engine's static check refuses a module that passes `$` to a closure defined inside `register`. `atom({ plugin, key })` takes string literals, not a const.
- The kit accepted a wrong tool-input shape at runtime that `tsc` caught: run the typecheck.

### Live checks

The test kit stands in for the engine; it can't show what the engine really does. Before building on an engine behavior the types don't state, probe it: a throwaway observer mod (`--plugin-dir`) that logs events with `$.fs.write`, and one short live session, with `--model haiku` to keep it cheap. Record the Claude Code version a behavior was checked on. Headless runs (`claude -p`) create transcript folders under `~/.claude/projects/`; run them from a scratch directory.

## Conventions
